# 🧭 Архітектура та посібник контриб'ютора

> Мапа проєкту для тих, хто хоче щось виправити чи додати, навіть якщо Rust для
> вас новий. Кожна типова зміна розписана до файлу.
>
> Читати згори вниз варто один раз: перші два розділи — **не про наш код**, а
> про систему, яку ми ставимо. Без них решта виглядає як набір довільних рішень.

## Що це

TUI-інсталятор власного дистрибутива на базі **Artix Linux з dinit**. Rust +
ratatui, три мови (укр / англ / ісп), працює **на фізичній консолі live-ISO**:
без графіки, без миші, без буфера обміну.

**systemd тут немає ніде** — ні на образі, ні в цілі, ні як запасний шлях. Це не
гасло, а вимога до коду: жодна перевірка, жоден скрипт і жодне пояснення в
коментарі не має спиратися на його поведінку. Половина хибних припущень у цьому
проєкті починалася зі знання, вивченого на systemd-дистрибутиві.

## Модель цільової системи

### Хто монтує корінь

**Не fstab.** Ланцюг такий:

```
прошивка → GRUB (grub.cfg на ESP)
              linux /boot/vmlinuz-linux root=UUID=… rw
                 → initramfs монтує корінь за цим UUID
                     → dinit стартує вже на змонтованому корені
```

Тобто корінь названо **в записі меню GRUB**, а `/etc/fstab` до цього моменту
ніхто не відкривав.

### Що робить fstab

На цій системі його читає **рівно одна служба**:

```
early-fs-fstab.target     type = scripted
                          command = /usr/bin/mount -a …
early-fs-local.target     waits-for: early-fs-fstab.target
```

З цього випливають дві речі, і обидві коштували часу, поки не були записані:

1. **Без fstab система вантажиться.** `mount -a` не має чого монтувати й
   завершується успішно. Втрачається лише те, що було в файлі, — swap, ESP,
   додаткові диски. Шкода **тиха**: машина виглядає справною.
2. **Навіть падіння цієї служби не спиняє старт**, бо наступна ціль чекає її
   через `waits-for` («дочекатись і йти далі»), а не `depends-on` («без цього
   не запускатись»).

Фатальним відсутній fstab стає лише там, де в ньому лежить потрібне для
запуску служб: `@log` для `/var/log` (без нього жодна служба dinit не відкриє
свій лог), окремі `/usr` чи `/var`, `/home` на іншому диску (менеджер входу
петляє).

**Практичний наслідок для тестів:** сценарій «зламати fstab» перевіряє
**діагностику й перезбирання файлу**, а не те, чи піднялася машина. Скрипт
`BREAK_FSTAB_SH` читає fstab перед видаленням і сам каже, який це випадок.

### Служби

- опис служби — файл у `/etc/dinit.d/<назва>` (пакетні — у `/usr/lib/dinit.d/`);
- **увімкнена** = симлінк у `/etc/dinit.d/boot.d/<назва>`;
- **mtime симлінка — це дата вмикання.** На цьому тримається список у режимі
  відновлення: те, що працює рік, не є причиною сьогоднішньої поломки, а те, що
  ввімкнули у вівторок, — цілком;
- вимкнути в непрацюючій системі: `dinitctl -o -d /etc/dinit.d disable <назва>`
  (`-o` обов'язковий: dinit у chroot не запущено);
- `depends-on` спиняє залежного при невдачі, `waits-for` — ні. Служба, яка
  ніколи не завершує старт, тримає завантаження **назавжди**, якщо в неї
  `start-timeout = 0`.

### Ланцюг завантаження UEFI

**Записи завантаження живуть у NVRAM прошивки, а не на диску.** `wipefs` і
`sgdisk --zap-all` про них не знають, тож перевстановлення лишає запис
попереднього — він указує на розділ, якого вже нема. Прибирає їх
`plan_prune_stale_boot_entries`, і лише ті, що осиротила **ця** установка
(GUID був на цільовому диску до неї і зник після).

Де лежить ESP — **одне джерело правди**, `system::disk::esp_mountpoint`:

| випадок | ESP | чому |
|---|---|---|
| звичайна установка | `/boot/efi` | ядра на корені, як в усьому світі |
| шифрування root-scope | `/boot` | ядра мають лежати поза контейнером |

Кожна установка додатково пише **знімний фолбек** `\EFI\BOOT\BOOTX64.EFI` — ним
вантажиться машина, що втратила запис у NVRAM.

## Межа, на якій усе тримається

> **Редактор збирає наміри. Диск чіпає тільки план.**

Жоден екран не виконує дій над диском. Екрани пишуть у `InstallConfig`;
`build_plan` перетворює його на `Vec<Action>`, де `Action { program, args }` —
просто дані; виконує їх `system/runner.rs` після підтвердження на екрані
підсумку.

Тому установку **перевіряють текстом**, не диском:

```rust
let t = plan_text(&build_plan(&app));
assert!(t.contains("groupadd -f log"));
```

Та сама межа в помічнику стенда (`tools/vm-setup` друкує план, файли чіпає
скрипт) і в редакторі розмітки (мітки видалення — наміри; `sgdisk` — план).

## Потік даних за 30 секунд

```
main.rs (термінал, головний цикл)
   └─ event.rs (роутинг клавіш; modal_open() — щоб Esc закривав модалку, а не екран)
       └─ screens/*.rs (draw() малює, handle_key() реагує, tick() дренує канали)
           └─ app.rs (App — увесь стан; InstallConfig — вибір користувача)
               └─ system/install/ (build_plan: вибір → список Action)
                   └─ system/runner.rs (виконує, стрімить лог у панель)
```

Поза цією лінійкою живуть **режими** з меню: відновлення, тест Wi-Fi, знос
дисків (TBW) і — лише у збірках `--devtools` — меню «Тест».

## Як улаштований `build_plan`

Найбільший файл, тож варто знати форму. `build_plan` **не містить** логіки
установки — він її **перелічує**:

```rust
pub fn build_plan(app: &App) -> Vec<Action> {
    // 0)  інструменти хоста
    // 1)  диск: розмітка, форматування, монтування
    // 2)  basestrap: база + обрані пакети
    // 3)  fstab (+ додаткові диски)     → перевіряє себе, див. нижче
    // ...
    // 9)  облікові записи               → plan_accounts()
    // 9c) initramfs + ключі LUKS        → plan_initramfs_luks()
    // 10) завантажувач                  → plan_bootloader()
    // 12) сервіси dinit + AUR           → plan_services()
    // 13) запис розмітки для відновлення → plan_install_manifest()
    // 13a) прибирання мертвих записів UEFI → plan_prune_stale_boot_entries()
}
```

Кожна `plan_*` — **чиста функція**: читає `InstallConfig`, дописує кроки.
**Порядок критичний** (fstab до завантажувача, акаунти до служб) — компілятор
його не перевірить.

**Крок fstab перевіряє власний результат.** `fstabgen` (Artix-івський, з
artools) викликається першим, але його слово не приймається на віру: у лог іде
код виходу й кількість рядків, далі вимагається запис для `/`, і якщо його нема
— файл складається самотужки. Генератор **один на двох** з режимом відновлення
(`recovery::fstab_gen_fn`, лише `findmnt` + `blkid`): це те саме питання,
задане двічі, і відповідь не має різнитися.

## Режим відновлення

Окремий вхід із меню режимів, для системи, яка вже не вантажиться.

- **питає роль КОЖНОГО розділу**, а не «де тут корінь»: доводити решту з
  `/etc/fstab` цілі хибно за побудовою — це файл, через який сюди й приходять;
- установка лишає по собі **запис розмітки** (`/etc/artix-tui/install.conf` і
  копія на ESP — саме вона працює, бо ESP не зашифрований); ролі беруться з
  нього за UUID, і над списком написано, **взято** їх чи **вгадано**;
- ремонти йдуть **у панелі стану** (потік + канал + `tick`), вирок — у
  заголовку панелі, а успішний ремонт **сам перезапускає діагностику** й
  ставить курсор на те, що лишилось зламаним. Так дві поломки лікуються тим
  самим циклом, що й одна;
- `chroot` лишається передачею термінала — він інтерактивний.

## Тестова інфраструктура

| Рівень | Що ловить |
|---|---|
| `cargo test` — план | текст плану: неправильний порядок, зниклий аргумент, забутий санітайзер |
| `cargo test` — рендер (`TestBackend`) | паніка в `draw()`, обрізана кнопка, сирий i18n-ключ |
| `cargo test` — запуск скриптів | шел-логіка, прогнана на підроблених деревах і мок-інструментах |
| меню «Тест» (`--devtools`) | ПОВНА установка за сценарієм, тоді поломка одним визначеним способом |
| `scripts/qemu-test.sh` | стенд: диски, прошивка, режими install/boot/bios/verify |
| `scripts/verify-vm.sh --nbd` | вирок по готовій системі, прочитаній з образу диска |

**Правило, що народилося з болю:** віддавати **перевірку**, а не лише механізм.
Читання коду перевіркою не є — режим відновлення був написаний саме так, і
ремонт завантажувача жодного разу не поставив завантажувач.

Скрипти, які щось руйнують, тестуються **запуском** через змінні оточення:
`FIXPERM_ROOT` (ремонт прав), `ARTIX_EFIBOOTMGR` / `ARTIX_OLD_PARTUUIDS` /
`ARTIX_LIVE_PARTUUIDS` (прибирання записів UEFI). Видаляти записи прошивки «за
читанням коду» не можна.

## Типові зміни

**Пакунок за замовчуванням** → `install/packages.rs`. Перевір, що він існує:
`pacman -T назва` (не `-Qq`); суфікси `-bin`/`-git` — це AUR.

**Текст** → однаковий ключ у трьох `i18n/*.toml`, вживання `t(app.lang, "…")`.
Literal у `.rs` заборонено — це ловить тест.

**Вбудований скрипт** → `src/assets/sh/*.sh`. POSIX sh: `sh -n`.

**Екран** → новий файл у `screens/`, варіант у `enum Screen`, один запис у
таблиці `step()`. Match без catch-all, тож незареєстрований екран — помилка
компіляції. Модалка → прапорець у `modal_open()`.

**Завантажувач** → гілка в `match c.bootloader` (`install/mod.rs`), пункт на
екрані опцій, i18n, README.

## Типи замість рядків

`InstallConfig` не зберігає вибір рядками: `boot_mode` — це `BootMode`,
`bootloader` — `Bootloader`, `gpu` — `Vec<GpuDriver>`. Додасте варіант до
`enum` — компілятор **змусить** обробити його всюди, включно з екраном вибору.

## Інваріанти

1. **Ніщо тут не має ламати машину, на якій воно запущене.** Перед `rm -rf` —
   `findmnt` на монтування всередині; відмова краща за видалення, що пішло не
   туди.
2. **Enter ніколи не мовчить**: відмова пояснюється рядком стану.
3. **Нічого довшого за ~100 мс в UI-потоці** — потік + канал + `tick`.
4. **Опція, що не може подіяти, не пропонується** (zswap без swap-розділу).
5. **Попереджати, а не забороняти**: деструктив називає втрати й вимагає
   свідомого підтвердження. Заборона ламає легітимні сценарії.
6. **У цілі ніколи `pacman -Sy` без `-u`** — частковий апгрейд убиває установку.
7. **`/tmp` і `/run` у цілі — свіжий tmpfs на КОЖЕН виклик `artix-chroot`.**
   Одноразовий скрипт віддавати одним `chroot(&script)`.

## Стиль

- Коментарі пояснюють **чому**, а не «що»; великі рішення — блоком над кодом.
- Коментарі й назви тестів — англійською; спілкування й документи — українською.
- Shell у `format!` — через `@@PLACEHOLDER@@` + `.replace()`, не через `{{`.
- Коміти: одна тема — один коміт; повідомлення описує наслідок для користувача.
